    Движок та середовище виконання (Runtime Engine):

    Браузери (Frontend): Використовують движки на кшталт V8 (Chrome, Edge), SpiderMonkey (Firefox) або JavaScriptCore (Safari) для взаємодії з DOM-деревом вебсторінки.

  7. Урок 0.6. Подключение JavaScript в HTML : 3:53
    Я це робив, я знає де він підключается, він у мене підключений в нульомому шаблоні за замочуванням.

    Розміщення та спосіб підключення тега <script> напряму впливають на швидкість завантаження сторінки та коректність роботи скриптів.

    1. Способи розміщення тега script

    • Перед закриваючим тегом </body> (Класичний безпечний спосіб):

      Браузер читає HTML-код зверху вниз. Якщо помістити скрипт у кінець документа, браузер спочатку повністю побудує інтерфейс (DOM-дерево), а вже потім виконає JS. Це гарантує, що користувач одразу побачить вміст, а скрипт матиме доступ до всіх елементів сторінки.

    • Всередині <head> з атрибутом defer (Сучасний стандарт):

      Звичайний тег <script> у <head> блокує відображення сторінки до повного завантаження файлу. Атрибут defer дозволяє завантажувати JS фоново, виконуючи його лише після завершення парсингу всього HTML.

    • З атрибутом async у <head> (Для незалежних скриптів):

      Скрипт завантажується фоново, але виконується миттєво після завантаження, не чекаючи готовності HTML. Підходить для лічильників аналітики та сторонніх віджетів.

    • Одразу після відкриваючого тега <body> (Специфічні випадки):

      Таке розміщення блокує парсинг HTML на самому початку. Застосовується рідко — наприклад, для швидкої зміни

      Варіант А: Атрибут defer (Відкладене виконання) Скрипт завантажується у фоні, але чекає, поки браузер повністю прочитає та побудує розмітку сторінки.

      Варіант Б: Атрибут async (Незалежне виконання) Скрипт завантажується у фоні та виконується одразу ж, як тільки файл завантажився, ставлячи парсинг HTML на паузу.

      Просте правило:Якщо скрипту потрібен доступ до DOM або збереження порядку з іншими скриптами $\rightarrow$ deferЯкщо це незалежний лічильник або реклама $\rightarrow$ asyncЗвичайний <script> без атрибутів у сучасній розробці розміщують або перед & lt; /body & gt; , або взагалі віддають перевагу defer у & lt; head & gt; .
    • Зовнішній файл (<script src="app.js"></script>):

      Розділяє структуру (HTML) та логіку (JS). Покращує читабельність коду та дозволяє браузеру кешувати файли.

    • Вбудований код (<script>/* код */</script>):

      Зручний для дрібних конфігурацій чи швидких тестів, але захаращує HTML-документ при збільшенні обсягу коду.

  11. Урок 0.8.3. Commit, push, branch, pull request, merge. Командная работа на GitHub : 19:37

    Ініціалізація та створення структури У терміналі Visual Studio Code виконайте серію команд для створення базового JavaScript-середовища:

    # 1. Ініціалізація Git git init # 2. Створення файлу конфігурації Node.js проєкту npm init -y # 3. Створення базових файлів розробки touch index.html index.js README.md .gitignore # 4. Створення конфігурацій linter/formatter (ESLint, Prettier, VSCode settings) touch .eslintrc.json .eslintignore .prettierrc .prettierignore mkdir .vscode touch .vscode/settings.json

    Заповнення .gitignore (Обов’язково!) Щоб системні та тимчасові файли не потрапляли на GitHub, відкрийте .gitignore і додайте:

    node_modules/ .DS_Store dist/ build/ *.log

    Крок А: Створення головної гілки та першого комміту

    # Створюємо/перейменовуємо головну гілку в main (або master) git branch -M main # Додаємо всі файли до staging git add . # Робимо перший комміт git commit -m "Initial commit"

    Крок Б: Зв'язування з GitHub та перший Push

    # Додаємо remote (замініть посилання на своє) git remote add origin https://github.com/USERNAME/REPOSITORY-NAME.git # Пушимо main на GitHub git push -u origin main

    Крок В: Комміти з номерами версій (як v0.0.1, v0.0.5) Коли ви досіваєте нові конфіги (ESLint, Prettier, Gulp) чи функції, ви робите новий комміт із назвою версії:

    # Додаємо змінені/нові файли git add . # Створюємо комміт з назвою версії git commit -m "v0.0.1" # Відправляємо на GitHub git push

    3. Робота з гілками (Feature Branches) Основне правило розробки: не писати код напряму в main (чи master). Для кожної нової функції створюється окрема гілка. Створення та перехід у нову гілку

    # Створити гілку 'feature/header' і одразу перейти в неї git checkout -b feature/header # Або сучасною командою: git switch -c feature/header

    Робота та комміти всередині нової гілки Всі файли, які ви створюєте чи редагуєте зараз, залишаються в гілці feature/header:

    # Додаємо зміни та комітимо git add . git commit -m "v0.0.2: добавлено шапку сайту"

    Заливання файлів у гілку (а не в main) Щоб відправити цю гілку на GitHub, вказуйте її назву при першому push:

    # Відправка гілки feature/header на GitHub git push -u origin feature/header

    Тепер на GitHub у випадаючому списку гілок з'явиться feature/header.

    4. Злиття гілок (Merge) та Pull Request Коли робота над фічею завершена, її потрібно об'єднати з головною гілкою (main). Локальне злиття через термінал:

    # 1. Переходимо назад у main git checkout main # 2. Затягуємо найновіші зміни з GitHub (якщо вони були) git pull origin main # 3. Вливаємо зміни з feature/header у main git merge feature/header # 4. Відправляємо оновлений main на GitHub git push origin main # 5. (Опціонально) Видаляємо локальну гілку фічі після злиття git branch -d feature/header

    5. Коли і як виконувати push та pull

    КомандаКоли виконувати?Як виконувати?

    git pull Завжди ПЕРЕД початком роботи або перед створенням нової гілки / перед git merge. Вона завантажує та об'єднує останні зміни з GitHub у ваш комп'ютер.git pull origin main

    git push ПІСЛЯ того, как зробили git commit і готові опублікувати свої зміни на GitHub.git push(або git push origin назва_гілки)

    6. Підсумковий щоденний Чек-лист розробника Початок дня / нової задачі:

    git checkout main git pull origin main git checkout -b feature/new-logic

    В процесі роботи:

    git add . git commit -m "v0.0.5"

    Завершення задачі:

    git push -u origin feature/new-logic git checkout main git merge feature/new-logic git push origin main

    Конфлікт мерджу (Merge Conflict) виникає тоді, коли Git не може автоматично визначити, які зміни правильні — наприклад, коли в одному й тому самому файлі та на тих самих рядках ви і хтось інший (або ви в іншій гілці) змінили код по-різному. Ось чіткий алгоритм дій для вирішення конфлікту через термінал та інтерфейс VS Code. Крок 1: Визначте, у яких файлах виник конфлікт Коли ви виконуєте git pull або git merge, і Git видає помилку CONFLICT, запустіть:

    git status

    У розділі Unmerged paths червоним кольором будуть виділені файли, які містять конфлікти. Крок 2: Відкрийте конфліктні файли у VS Code Коли ви відкриєте такий файл у Visual Studio Code, ви побачите спеціальні маркери конфлікту:

    <<<<<< HEAD (Поточні зміни / Current Change) console.log("Ваш код, який знаходиться у вашій поточній гілці");=======console.log("Код з іншої гілки або з GitHub, який ви намагаєтеся затягнути");>>>>>>> branch-name (Прихідні зміни / Incoming Change)

    VS Code підсвічує ці блоки та пропонує швидкі кнопки над кодом: Accept Current Change — залишити ваш локальний код. Accept Incoming Change — прийняти код з гілки, яку вливаєте (або з GitHub). Accept Both Changes — зберегти обидва варіанти один за одним. Compare Changes — відкрити порівняння файлів поруч. Ви можете просто натиснути потрібну кнопку або відредагувати файл вручну, видаливши всі службові символи ( <<<<<<<,=======,>>>>>>>) та залишивши лише правильний підсумковий код.

    Крок 3: Зафіксуйте вирішення конфлікту Після того як усі конфліктні файли відредаговані та збережені (Ctrl + S):

    # 1. Позначте конфліктні файли як вирішені (додайте їх у staging) git add . # 2. Перевірте стан (все має бути зеленим) git status # 3. Завершіть процес злиття коммітом git commit -m "Fix merge conflict" # 4. Відправте оновлений стан на GitHub git push

    Що робити, якщо ви заплуталися і хочете скасувати злиття? Якщо під час вирішення конфлікту щось пішло не так і ви хочете повернути все, як було до запуску pull чи merge:

    git merge --abort

    Ця команда скасує спробу злиття і поверне ваш проект у безпечний стан до виникнення конфлікту.
